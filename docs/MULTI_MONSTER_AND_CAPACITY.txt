다중 슬라임 사냥 구역 — 2026-10-09

실행
Play.cmd로 실행한다. 초원 시작 위치의 연습용 슬라임 1마리와 동쪽 사냥 구역의 4마리가 있다.
동쪽 사냥 구역 좌표: (7,-4), (10,-4), (7,1), (11,1).
방향키로 가까이 이동하고 Z를 누른다. 클라이언트는 가장 가까운 살아 있는 몬스터의 ID를 선택한다.
서버가 거리 1.5와 공격 간격 0.4초를 다시 검사한다. 3회 타격 시 조각 1개와 처치 수 1이 저장된다.
체력 바는 서버가 보낸 HP다. 사망한 몬스터는 사라지고 3초 후 해당 자리에서 재생성된다.
현재 AI 이동·반격·경험치·레벨업·스킬은 추가하지 않았다.

코드 읽는 순서
1. src/Protocol/planet.proto: Command.target_id, Update.monsters, MonsterView.id/spawn_zone.
2. UnityClient/Assets/Scripts/UI/Presentation/GameConnection.cs: NearestTarget가 대상 ID만 선택한다.
3. src/Server/World.cs: attack에서 현재 방의 대상만 찾고 거리/쿨다운을 검사한다.
4. src/Server/MonsterPopulation.cs: 방에 속한 몬스터 목록과 HP, 죽음, 재생성 상태를 관리한다.
5. World.SaveProgress: 치명타에서는 보상 저장에 성공한 다음 메모리의 보상과 사망 상태를 확정한다.
6. PreviewWorld.cs: 서버 목록을 ID별 객체로 반영한다. SlimeHealthDisplay.cs는 서버 HP를 표시한다.
7. tests/Program.cs: 동시 치명타, 저장 실패, 재생성, 오래된 ID, 채널/지역 격리 검증.

설계 결정
- 몬스터 ID에는 채널/지역/스폰 슬롯/재생성 횟수가 포함된다.
- 재생성 때 ID를 바꿔 죽기 전 대상에 대한 지연 요청이 새 몬스터를 때리지 못하게 한다.
- 서로 다른 채널/지역의 ID와 존재하지 않는 ID는 거부한다.
- 마지막 체력 1에서 저장이 실패하면 보상도 사망도 확정하지 않는다.
- 같은 채널의 상태 변경을 직렬화하여 동시에 들어온 치명타 중 하나만 보상을 확정한다.
- 기존 단일 슬라임 데모 호환을 위해 Update.monster와 빈 대상 ID의 첫 슬롯 공격을 유지한다.
  새 Unity 클라이언트는 항상 명시적인 대상 ID를 전송한다.
- 몬스터 HP와 재생성은 일시적인 월드 상태다. 서버 재시작 시 몬스터는 새로 생성된다.
- 현재 재생성 시각은 방을 읽을 때 갱신한다. 플레이 중에는 클라이언트 요청으로 갱신되며,
  독립적인 지역 처리 루프/AI 틱을 구현한 것은 아니다.
- 보상 규칙은 마지막 타격자에게 지급이다. 기여도/파티 분배 규칙은 아직 없다.

서버 배치와 1,000명 목표
현재 서버는 본인 PC에서 실행되는 별도의 .NET 프로세스다. Unity 클라이언트와 분리되어 있다.
플레이어 클라이언트 자체가 서버가 되는 호스트 방식이 아니라 전용 서버 프로그램 방식이며,
전용 물리 서버나 클라우드 VM에 배포한 상태는 아니다. Unity/.NET 무료 클라우드 서버를 쓰지 않는다.
GameHost는 루프백(127.0.0.1)에 바인딩한다. 현재는 같은 PC의 접속만 받는다.
기본값: 전체 연결 128, 채널당 32. 이 숫자는 허용 상한이며 보장된 동시 접속 성능이 아니다.

상한만 1,000으로 바꾸면 안 되는 이유
- 각 응답은 같은 지역 플레이어 전체를 포함한다. 주변 대상만 보내는 AOI/변경분 전송이 없다.
- 프레임 상한은 32,768바이트다. 밀집한 지역의 전체 목록은 이 제한을 넘을 수 있다.
- 저장을 기다리는 동안 같은 채널의 게임 요청이 기다린다. 지역별 처리와 저장 지연 분리가 필요하다.
- 계측, 실 부하/장시간 테스트, 접속 폭주 제어, 저장 장애·재접속 복구 검증이 더 필요하다.
- 외부 접속 주소·인증서·배포·모니터링·백업/복구도 운영 환경에 맞게 구성해야 한다.
따라서 지금은 1,000명을 허용하거나 처리할 수 있다고 검증한 상태가 아니다.
