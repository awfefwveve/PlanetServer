부하테스트 사용법과 이번 결과 — 2026-10-11

실행 (PlanetServer 폴더의 PowerShell에서)
  .\scripts\LoadTest.ps1 -Clients 200 -Seconds 20 -Scenario crowded
  .\scripts\LoadTest.ps1 -Clients 1000 -Seconds 20 -Scenario spread
crowded: 한 채널/한 지역 밀집. spread: 30개 채널에 고르게 분산.
결과는 load-results의 날짜-인원-조건.json에 저장된다. 오류 또는 인원 이탈 시 종료코드1.
원래 게임 서버를 켤 필요가 없다. 이 도구가 별도의 임시 포트로 테스트 서버를 실행하고 종료한다.
게임/Unity/사용자 DB/운영 정원 설정은 수정하지 않는다. 최대1000명, 측정2~120초.
각 실행의 테스트 계정·인증서·서버 로그는 run-... 디렉터리에 보존하고 Git에서는 제외한다.

도구 구성
부하 발생기 → 실제 TCP/TLS 연결 → Protobuf 요청 → 별도 프로세스의 GameHost/World.
서버는 기존 서버 구현을 그대로 사용하며 테스트 채널 정원만 요청 인원으로 설정한다.
계정은 측정 전에 파일 저장소에 준비하고 로그인/채널 입장은 최대8개씩 진행한다.
일찍 들어온 클라이언트도 준비 중 상태 조회를 계속해 서버의 유휴 연결 제한에 걸리지 않는다.
측정 중 이동/상태 조회를 교대로 요청하고 매 응답 뒤100ms를 기다린다.
따라서 개당 최대10req/s이며 응답이 늦으면 실제 발생 부하가 감소하는 closed-loop 검사다.
빠른 탭·UI·그래픽 프레임 성능 검사가 아니다. 공격/보상/채팅/포탈/PG 저장 부하는 이번 도구에 없다.
로그인 폭주, 패킷 지연·유실, 강제 장애·복구, 재시작 후 저장 정합성, 장시간 시험도 별도다.

CPU 설명
실서비스에서 서버 판정은 서버 컴퓨터 CPU가 담당하고 사용자의 입력/렌더링은 사용자 PC가 담당한다.
가짜 클라이언트는 렌더링 없이 네트워크 요청만 만든다. 한 발생기가 많은 사용자 PC를 흉내 낼 수 있다.
이번에는 서버와 발생기의 프로세스를 분리해서 각각의 CPU/메모리를 측정했지만 물리 PC는 같다.
경쟁 자원이 있고 인터넷 지연도 없으므로 최종 용량으로 환산할 수 없다.
다른 PC 발생기는 클라이언트1000대가 필요하다는 뜻이 아니라 충분한 발생기1대 이상을 뜻한다.
현재 서버 리스너는 loopback 전용이며 이 도구도 로컬 모드다. 원격 모드는 아직 구현하지 않았다.
CPU 비율은 논리32개 전체 기준이다. 채널 처리가 한 코어에서 막히면 전체 비율이 낮을 수 있다.
메모리는250ms 주기의 WorkingSet 표본 최댓값이며 전 과정의 절대 최대치가 아니다.

이번 결과 (15~20초의 1차 시험)
200명 한 지역: 유지200, p99 7.75ms, 약1848응답/s, 오류0.
500명 한 지역: 유지500, p99 34.51ms, 약4139응답/s, 오류0.
1000명 한 지역: 총입장995, 측정시작/종료691, 준비 중309접속 실패/이탈, 남은 요청p99 538.87ms.
1000명 30채널 분산: 유지1000, p99 13.29ms, 약9116응답/s, 오류0.
1000밀집의 p99는 1000명 전원을 처리한 수치가 아니라 살아남은691명의 수치다.
종료 시 미완료 요청을 취소하므로 attempts와replies 차이는 별도로 해석해야 한다.
최대 인원/상용화 인증 결과가 아니고, 500명 장시간 안정성을 보증하지 않는다.

발견 사항
밀집 실패 서버 로그에 InvalidDataException309건이 있다.
World.Snapshot은 같은 지역 전체 플레이어를 응답마다 포함하고 Framing은32768바이트로 제한한다.
전체 목록 응답 크기가 프레임 제한을 넘는 경로가 유력한 원인이다. 예외 메시지/실패 응답 크기를
추가 계측해 확정해야 한다. 프레임 상한만 늘려서 해결됐다고 볼 수 없으며 AOI/차분 전송 검토가 필요하다.
이번 작업은 부하 도구 제작과 측정이다. 해당 서버 구조를 변경한 작업은 아니다.
