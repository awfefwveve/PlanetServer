# 인트로 · 월드 선택 · 캐릭터 생성과 선택

## 실행 흐름

Play.cmd → 이용 안내 → 로고 → 월드 목록 로딩 표현 → 월드 선택 → 계정 인증과 캐릭터 목록 조회 → 캐릭터 선택.
빈 슬롯을 선택하면 분류 → 캐릭터 유형 → 이름·외형 → 서버 저장 → 선택 화면으로 이어진다.
게임 시작을 누르면 서버가 캐릭터 소유권을 검사한 뒤 입장시키고, 이야기·도착 화면을 거쳐 맵을 표시한다.
이야기와 도착 화면은 자동으로 넘어가며 ESC 또는 건너뛰기로 생략할 수 있다.
게임에서 ESC → 캐릭터 선택 → 예를 누르면 진행 상태 저장 후 선택 화면으로 돌아온다.

실제 월드는 `meadow` 하나다. 다른 월드 아이콘은 비활성화한다. 월드 목록을 원격 디렉터리 서비스에서 가져오는 구조는 아직 아니다.
계정 인증은 기존 로컬 런처의 테스트 계정을 사용한다. 별도 회원가입·로그인 화면, 계정 복구, 2차 비밀번호는 구현하지 않았다.
인트로·이야기는 명세 기반 화면 전환과 임시 그래픽이다. 원작 영상·음원 파일을 가져온 것은 아니다.

## 책임과 데이터

| 부분 | 책임 |
|---|---|
| StartupView / CharacterSelectionView / CharacterCreationView | 화면과 사용자 입력 |
| LobbyCoordinator | 목록 조회·이름 확인·생성·입장·선택 복귀의 비동기 흐름 |
| PreviewUiController / UiModel | 화면 상태·선택 상태·작업 중 입력 잠금 |
| GameConnection | 요청을 순서대로 TCP/TLS로 전송하고 응답을 해당 요청에 전달 |
| CharacterCatalog | 이름·외형·슬롯 수 검사, 생성 및 이전 데이터 이관 |
| World | 계정 세션, 선택 캐릭터 소유권, 월드 입장·퇴장, 진행 상태 |
| FileStore / PostgresStore | revision을 사용한 저장과 충돌 검출 |

계정 인증 정보와 캐릭터 모델을 논리적으로 분리했다. 계정은 최대 12개의 CharacterData를 소유하고,
각 캐릭터는 고유 ID, 이름, CharacterLook, 위치, 처치 수, 조각, 골드, 퀘스트 완료 여부를 가진다.
현재 저장 단위는 계정 aggregate다. 파일은 계정 JSON 하나, PostgreSQL은 계정 payload JSONB 하나에
캐릭터 배열을 보관한다. 캐릭터별 독립 테이블로 나눴다는 의미는 아니다.
PostgreSQL에는 이름 예약용 planet_character_names 테이블을 추가했다. 이름 고유 제약과
계정 payload 변경을 같은 트랜잭션으로 처리한다. 캐릭터별 테이블·인벤토리 정규화는 콘텐츠 확대 시 별도 이관한다.

서버는 이름을 정규화하고 한글·영문·숫자 2~12자로 제한한다. 계정 전체에 걸쳐 이름이 중복되지 않는다.
이름 확인은 예약이 아니므로 생성 시 다시 확인하며 DB 고유 제약도 적용한다.
파일 모드는 한 프로세스 World 잠금 안에서 확인·저장한다. 여러 서버 프로세스 운영을 지원하지 않는다.
외형 값의 허용 범위와 캐릭터 소유권은 UI를 우회한 패킷에도 적용한다.
캐릭터 유형은 현재 외형/선택 메타데이터이며 실제 직업별 스킬·스탯 차이는 아직 없다.

## 기존 데이터

Characters 필드가 없거나 null인 기존 계정은 첫 로비 로그인 시 이전 위치·보상을 가진 캐릭터 하나로 이관한다.
기존 계정 이름은 이관 캐릭터 이름으로 유지한다. 이 이름은 신규 캐릭터의 이름 규칙보다 길거나 밑줄을 포함할 수 있다.
다른 신규 캐릭터가 아직 이관하지 않은 기존 계정 이름을 선점하지 못하게 검사한다.
이관은 저장 성공 뒤에만 메모리에 적용한다. 계정의 이전 진행 필드는 구형 데모 호환을 위해 남겨 두었다.
새 실행 경로와 구형 데모는 저장된 진행 정보를 상호 동기화하지 않으므로 일상 개발은 Play.cmd를 사용한다.

## 검증

- 서버 검사 58개 통과: 기존 인증·전투·이동·저장, 로비 진입, 위조 외형, 다른 계정 캐릭터 접근, 동시 이름 중복, 저장 실패, 12슬롯 제한, 캐릭터별 위치, 서버 재생성, 이전 데이터 이관.
- PostgreSQL 검사 포함: 외형 저장, 정규화된 이름 조회, 고유 제약 실패 시 계정 payload와 revision 롤백.
- VerifyLobby.ps1: Unity에서 버튼 동작으로 생성·입장·선택 복귀, 실제 서버 프로세스를 종료하고 재시작한 뒤 ID·외형·위치 복원.
- VerifyUI.ps1: 기존 25화면·116개 배치와 3해상도 회귀 검사.
- PlayMap.ps1 -Verify: 기존 두 클라이언트 맵·전투 연결 회귀 검사.

UI 자동 검증은 버튼의 실제 리스너를 호출하는 방식이다. 모든 화면을 물리적 마우스·키보드로 수동 검사했다는 뜻은 아니다.
강제 프로세스 종료 직전 이동 저장, WAN 지연·패킷 손실, 대규모 동접, 계정 잠금·복구·보안 운영은 별도 작업이다.

## Git

작업 브랜치: feature/character-lobby. 이전 기준점: map-movement-v1.
데이터 스키마가 바뀌었으므로 소스를 되돌리는 것과 저장 데이터를 되돌리는 것은 다르다.
Git은 계정 데이터와 인증서를 추적하지 않는다. 실제 데이터로 스키마 이관할 때는 먼저 별도 백업을 만든다.
